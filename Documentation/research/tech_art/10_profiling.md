## 1. How professional teams profile before they optimise

### 1.1 Budgets are in milliseconds, split per pass
- Unity's own guidance: watch frame time, not fps; 33.33 ms is the 30 fps budget and 16.66 ms the 60 fps budget, and "even a single frame that exceeds the target frame budget will cause hitches" [P20].
- On mobile, Unity says to leave about 35 % of the frame idle so the chip can cool: a 30 fps target then gets about 22 ms of work ((1000 / 30) x 0.65 = 21.66 ms) [P20]. The same page says 60 fps on mobile drains the battery about twice as fast as 30 fps [P20].
- Real per-pass budget from an indoor first-person game: Rainbow Six Siege (Ubisoft Montreal, GDC 2016) had to run at 60 fps on Xbox One and PS4 with destruction [P22]. Its slides give average GPU times of about 5 ms for geometry, 5 ms for lighting (SSR included), 4 ms for post-processing and other full-screen work, with SSAO and the SSR ray trace on async compute, a "max 4ms linear spent on opaque pass" line that sits among the CPU critical-path items (most likely CPU submission time, not a GPU cap; claim check 15 #13), and a CPU critical path of about 10 ms average [P21]. Checkerboard rendering let them keep nearly the per-pixel budget of a 30 fps game, and the abstract says it cut rendering time by up to 50 % with little quality loss [P21][P22]. These numbers were first read from search snippets and then checked against archive.org's OCR text of the deck (15 #13), not from the slide images (see Sources).
- What to take from it (inference): a team sets a budget per pass family before the content exists, caps the open-ended passes (opaque geometry, shadows), and treats post and full-screen work as a fixed block. A 60 fps desktop frame for FrontRooms has 16.7 ms; a starting split to test against, before measurement, could be: shadows 3 ms, depth-normals prepass + SSAO 2 ms, opaque forward 5 ms, transparent and glass 1.5 ms, post (bloom, uber, LUT) 1.5 ms, headroom 3.7 ms. ESTIMATE: 3 + 2 + 5 + 1.5 + 1.5 = 13 ms, 16.7 - 13 = 3.7 ms headroom. This split is a placeholder for the M stage; it is not measured.

### 1.2 Decide CPU-bound or GPU-bound before touching anything
- Unity markers: a main thread that is busy for the whole frame with no waiting marker means CPU-bound; a main thread sitting in Gfx.WaitForPresentOnGfxThread while the render thread sits in Gfx.PresentFrame means GPU-bound; WaitForTargetFPS is only the frame limiter's padding [P20].
- FrameTimingManager / the Highlights module give the same split as two numbers, CPU Active Time and GPU Time, against a target frame time (section 2.2) [P5].
- Apple's Instruments method for the same question: find a long Display interval; if the GPU tracks show a long fragment stage, the shader cores are the limit; if the GPU tracks have gaps and the render thread shows little blocked time, the CPU is the limit (a healthy render thread was about 75 % blocked in Apple's example) [P23].
- The resolution test: Apple suggests temporarily shrinking the viewport; if the frame gets faster, the fragment side is the limit [P23]. FrontRooms already did this once in WebGL: going from 2560 x 1440 to 1280 x 720 did not change the title corridor frame time, so that frame was per-draw CPU bound there [P40].
- On NVIDIA hardware the vendor method is top-down: take the most expensive GPU ranges, read each unit's percent of peak throughput (SOL%), and decide throughput-limited (top unit above 80 %) or latency-limited (below 60 %) [P24]. Apple's equivalent is the performance-limiter counters (section 3) [P17].

### 1.3 Measure a player build on the target hardware
- Unity: "the most accurate profiling results always come from running and profiling builds on target devices"; the Editor is for finding the main issues quickly [P20]. The same project can be CPU-bound on one device and GPU-bound on another, so each target is measured [P20].
- The Profiler needs a Development Build (debug symbols, Profiler enabled); Autoconnect bakes the Editor's IP into the player; Deep Profiling adds overhead [P25]. Unity says deep profiling distorts relative timings, so normal markers are used for comparisons [P20].
- The GPU Usage module cannot profile the Editor itself, and Windows Editor Play-mode numbers carry Editor overhead [P1].
- Project evidence of the gap: FrontRooms' title corridor cost 7.2 ms in the Mac Editor and 33 ms of wasm main thread in the WebGL build on the same machine, about 4.6 x [P40]. The Editor's "frame ms" in that note includes Editor overhead [P40].

### 1.4 Capture discipline
- Same section, same camera, before and after. Unity's Profile Analyzer workflow is: a repeatable scripted or fixed playthrough, a "before" capture, the change, an "after" capture of the same section, then compare median frames and marker medians [P26].
- Warm up, then measure a fixed count. Unity's Performance Testing package warms up for at least 80 ms or 3 rendered frames by default and then measures about 500 ms of frames; both counts can be set explicitly (WarmupCount, MeasurementCount) [P27]. The FrontRooms bench of 2026-10 let each view settle 15 frames, recorded 60 frames, then timed 12 synchronised renders [P40].
- Remove the frame cap when measuring cost. The 2026-10 bench set targetFrameRate -1 and vSync 0 [P40]; Unity notes that markers look different with VSync on and off [P20]. In this project the Medium, High, Very High and Ultra quality levels have vSyncCount 1 (`ProjectSettings/QualitySettings.asset`, read 2026-11-04) [P48], so a capture that keeps the shipped quality level must turn VSync off or read GPU time instead of frame time (inference).
- Keep the machine quiet. PIX's guidance is to not interact with the computer while timing data is collected and to close other GPU apps [P33]. The 2026-10 FrontRooms runs were partly taken while other sessions' Unity batch jobs loaded the Mac (load average 68-107), and those timings were marked noisy; counts were unaffected [P40].
- Control the thermal and power state on Apple devices:
  - Xcode device conditions can hold an iPhone/iPad at a thermal state floor (fair, serious, critical) without heating it; at "serious" the system expects apps to cut CPU, GPU and I/O [P28].
  - Xcode 13 added a GPU Performance State device condition, a performance-state choice in Instruments' recording options, and a GPU performance state track in Metal System Trace [P29].
  - The Metal debugger profiles a capture at the GPU performance state the device had at capture time, unless a state is induced from the debug bar [P30]; its replay is not affected by thermals, while a live Metal System Trace is [P17].
  - On the Mac, Game Mode gives a full-screen game priority on CPU and GPU (Apple silicon, macOS 14+) [P31]; the Metal Performance HUD shows whether Game Mode is on [P32]. Inference: a Mac player capture is taken full-screen, on power, with the HUD's Game Mode state written in the log.
- Report distributions, not one number: median plus p95/p99 frame time, and the longest frame, as the 2026-10 harness did (p95 51-52 ms, p99 68-77 ms) [P40].

## 2. Unity 6 tools for URP 17, and what each shows on macOS Metal

All pages below are the Unity 6.6 (6000.6) manual unless a row says otherwise; this project runs 6000.6.3f1 with URP 17.6.0.

### 2.1 Unity Profiler: GPU Usage module (does not work on Metal)
- The GPU Usage module is "Not supported" on macOS Metal and on iOS/tvOS Metal; the page says to use Xcode's GPU Frame Debugger instead [P1]. It is supported on Windows D3D11, D3D12 and OpenGL, and not on Vulkan or WebGL [P1].
- It only profiles Play mode or builds, never the Editor itself; it is off by default; it does not work when Graphics Jobs is on [P1]. On Windows the Editor's Play mode can be profiled with D3D11/D3D12, with Editor overhead in the numbers [P1].
- Its chart categories (Opaque, Transparent, Shadows/Depth, Deferred, PostProcess) are named for the Built-in pipeline; SRP work lands in "Other" [P1]. So even on Windows, URP pass times come from the Hierarchy view (sampler names), not from the chart colours (inference from [P1]).
- Consequence for FrontRooms: the Mac Editor and the Mac/iOS players give no per-pass GPU ms in the Unity Profiler. GPU ms per pass on Apple hardware comes from Xcode (section 3) or from URP's own Detailed Stats (2.3) if the GPU recorder works on Metal (UNCONFIRMED FOR 6000.6, see 2.3).

### 2.2 FrameTimingManager and the Highlights module (CPU vs GPU bound, works on Metal)
- FrameTimingManager is supported on macOS Metal and iOS Metal; WebGL is partial (no GPU frame time) [P2].
- It is always active in development builds and the Editor; release builds need Player > Other Settings > Rendering > Frame Timing Stats, unless the data is read through ProfilerRecorder [P3].
- Results arrive with a fixed four-frame delay; GPU results are read three frames late [P2].
- Metal caveat, from the page: on tile-based deferred GPUs "the reported GPU time might be larger than the reported frame time", because gaps between deferred phases count as GPU time [P2]. So on Apple GPUs gpuFrameTime is an upper bound, not a pass sum (inference from [P2]).
- Counters by name (for ProfilerRecorder, values in nanoseconds): "CPU Total Frame Time", "CPU Main Thread Frame Time" (PlayerLoop minus waits for render thread, present and target FPS), "CPU Render Thread Frame Time" (RenderLoop minus Gfx.PresentFrame), "GPU Frame Time"; cpuMainThreadPresentWaitTime has no counter [P4].
- The Highlights module (off by default) marks frames where CPU Active Time (the longer of main and render thread, waits removed) or GPU Time (first GPU command of the frame to GPU completion) passed the target frame time, and with a frame range selected counts the over-budget frames per resource in a Bottlenecks section [P5].
- Project evidence: the 2026-10 bench got gpuFrameTime = 0 in batch mode on the M3 Max, and render-thread time 0 too [P40]; the 2026-11-04 clone probe (6000.6.3f1, batch Play mode, Metal) again read gpuFrameTime 0.00 in every view, and SystemInfo.supportsGpuRecorder was False [P41]. The manual does not mention batch mode [P2][P3]. Inference: batch mode presents no frame, so GPU timing must be taken in a windowed (non-batch) Editor Play session or in a player, and on Apple hardware the per-pass split comes from Xcode (section 3).

### 2.3 URP Rendering Debugger (Display Stats has per-pass GPU ms)
- Display Stats (Play mode only): Frame Stats are average/min/max over the 30 most recent frames (Frame Rate, Frame Time, CPU Main Thread Frame, CPU Render Thread Frame, CPU Present Wait, GPU Frame) [P11]. Bottlenecks gives the share of the last 60 frames that were CPU, GPU, Present-limited or Balanced, and is only available "when you build your player on a device" [P11]. With VSync on, Present-limited is close to 100 % [P11].
- Detailed Stats lists ms per rendering step (Profiling Scopes) with three columns: CPU (command buffer execution on the render thread), CPUInline (main-thread code) and GPU (GPU execution time), per frame or averaged over one second [P11]. The page has no platform note [P11]. GPU timing of a ProfilingSampler goes through the GPU Recorder, which needs SystemInfo.supportsGpuRecorder and lags three frames [P19]. Whether supportsGpuRecorder is true on Metal is not stated in the docs. Measured: it is False in Editor batch mode on the M3 Max with 6000.6.3f1 [P41], so the GPU column is empty there. In a windowed Editor or a Mac/iOS player it is UNCONFIRMED FOR 6000.6; the dev overlay (row P-1) prints it once per run.
- Rendering tab: an Overdraw debug view ("check where Unity draws pixels over one other"), map overlays (depth, main-light shadow map, additional-light shadow atlas), pixel validation (NaN/Inf/negative, out-of-range), lighting debug modes (shadow cascades, lighting with/without normal maps, reflections) and material validation (albedo luminance, metallic range) [P11]. The 6000.6 reference names no "overdraw mode" values or max count [P11].
- In a build: only in Development builds; LeftCtrl+Delete on macOS (LeftCtrl+Backspace elsewhere), three-finger double tap on touch [P12]. All tabs other than Display Stats need Strip Debug Variants off in URP Global Settings, otherwise only Display Stats is available [P12].

### 2.4 Frame Debugger (draw list, SRP Batcher breaks, load/store per pass)
- Steps through every rendering event of one frame; works in URP [P8]. It cannot show GPU time (the event panel has no timing field) [P9].
- Per event it shows the render target with Size, Format, Color Actions, Depth Actions, Memoryless, clears; blend state; Draw Calls, Vertices, Indices; "Batch cause" (why the SRP Batcher could not batch this event with the previous one); Meshes, Pass, LightMode; used and original shader; ZTest/ZWrite/Cull; stencil; and all keywords, textures and constants [P9].
- SRP Batcher check: Render Camera > Render Opaques > RenderLoopNewBatcher.Draw > select an SRP Batch; each batch shows its draw count, keywords and the break reason, e.g. "Nodes have different shaders"; many small SRP batches usually mean too many shader variants [P7].
- Attach to a player: Development Build, a platform with multithreaded rendering (every platform except Web), and Run In Background on desktop [P10]. So WebGL cannot be inspected with it (inference from [P10]).
- On Metal it works in the Editor and in a Mac or iOS dev player; it shows what URP asked for (actions, targets), not what the Apple GPU did with it (inference; Xcode is needed for that, section 3).

### 2.5 Render Graph Viewer (URP 17)
- Shows the frame's render graph: resources down the side, passes in execution order, an access block per pass and resource; a blue bar under passes that URP merged into one native render pass; "Pass break reasoning" for why a pass could not merge with the next; per-resource Load Action / Store Action, Samples, BindMS, Clear and Memoryless (tile-memory) flags; a Load/Store Actions view option (blue clear, green load, red store, grey don't-care) [P13 (6000.3 page)].
- It can target the Editor, a local player, a remote player or a direct IP connection [P13].
- Why it matters on Apple: every extra store/load between passes is system-memory traffic on a tile GPU [P18]; this window is the cheapest way to see where URP breaks a native render pass before opening Xcode (inference).

### 2.6 ProfilerRecorder counters at runtime (and what 6000.6.3f1 really exposes)
- The manual: Rendering module counters are readable in players through ProfilerRecorder, and "high level counters are also available in Release Player" [P6]. Marked available in release players: SetPass Calls, Draw Calls, Batches, Triangles, Vertices, Render Textures (count and changes), Used Buffers, vertex/index buffer upload in frame, Shadow Casters Count; not in release: the static-batching and instancing breakdowns and Used Textures [P6]. Its code example starts recorders named "SetPass Calls Count", "Draw Calls Count" and "Vertices Count" [P6].
- Measured in 6000.6.3f1 (clone probe, Editor batch mode): the list of available counters has no "Draw Calls Count" and no "Batches Count". It has split draw counters instead: "Standard Draw Calls Count", "Standard Indirect Draw Calls Count", "Standard Instanced Draw Calls Count", "SRP Batcher Draw Calls Count", "BRG Draw Calls Count", "BRG Indirect Draw Calls Count", "Null Geometry Draw Calls Count" (and "Null Geometry Indirect"), each with a matching "... Instances Count"; plus "SetPass Calls Count", "Triangles Count", "Vertices Count", "Shadow Casters Count", "Render Textures Changes Count", "Used Buffers Count", "Used Textures Count/Bytes", "Video Memory Bytes", the dynamic/static/instanced batching counters, and the four frame-timing counters [P41]. Recorders started with "Draw Calls Count" and "Batches Count" read 0 in all 75 view x variant rows, while "SetPass Calls Count" and "Triangles Count" matched UnityStats in every row [P41].
- So for 6000.6 the manual's draw-call example is behind the engine (inference from [P6] vs [P41]). A runtime overlay sums the split draw counters and checks `ProfilerRecorder.Valid` for every name, and the ratio "SRP Batcher Instances Count / SRP Batcher Draw Calls Count" gives objects per SRP batch for free (inference; the probe did not record the split values yet).

## 3. Apple: Xcode Metal capture, Instruments, counters, TBDR waste

### 3.1 Getting a Metal capture of a Unity Mac or iOS build
- Unity's integration (6000.6): on macOS, iOS and tvOS Xcode can analyse frames of a running Unity app; on macOS also frames of the Unity Editor; only with Metal [P14].
  - Editor: in Xcode make or open a macOS project, Edit Scheme > Info > Executable = Unity Editor, GPU Frame Capture = Metal, optionally `-projectPath` in Arguments; run it from Xcode; then press the "Xcode Capture" button to the right of the Scene or Game view, Xcode's camera button, or call the FrameCapture API [P14]. Without Xcode: start the Editor with `-enable-metal-capture` and call `FrameCapture.BeginCaptureToFile` / `EndCapture` from code; Xcode then saves captures to disk [P14].
  - Mac player: an empty macOS Xcode project whose scheme Executable is the built .app, GPU Frame Capture = Metal; press the camera button or use the FrameCapture API; or launch the player with `-enable-metal-capture` and use the API [P14].
  - iOS: the command-line route is not supported; build the Xcode project from Unity and always launch from Xcode, then use the Xcode UI or the FrameCapture API [P14].
- `UnityEngine.Apple.FrameCapture` has BeginCaptureToFile, BeginCaptureToXcode, CaptureNextFrameToFile, CaptureNextFrameToXcode, EndCapture and IsDestinationSupported [P15]. CaptureNextFrameToFile brackets exactly one frame [P15], which is what a fixed-view capture key needs (row P-4).
- Apple's side: an app not started by Xcode may capture if its Info.plist has `MetalCaptureEnabled` = YES, or on macOS 14+ if it runs with `MTL_CAPTURE_ENABLED=1`; enabling capture has "a tiny, but measurable" CPU cost, so Apple suggests turning it on only for some builds; a capture to file needs `supportsDestination(.gpuTraceDocument)` and a `.gputrace` output name; a capture may span several frames [P16].
- Validation is not timing: Unity's "Metal API Validation" player setting is Unity's own in-Editor shader binding check and "doesn't enable Apple's Metal API validation"; Apple's validation is turned on by setting Run in Xcode as = Debug in Build Profiles [P34]. Inference: time only Release-configured runs with validation off; use Debug runs to find errors. This project has `metalAPIValidation: 1` and `metalEditorSupport: 1` (`ProjectSettings/ProjectSettings.asset:242-243`) [P48], i.e. Unity's Editor-side check, which does not affect a player.
- A profiled trace can be exported with "Embed performance data" and opened on any Mac without replaying [P30]: this is how a capture from the clone is handed to 游戏视觉 or 总控 (inference).

### 3.2 What the Metal debugger shows
- Profile after replay (or the Profile button) gathers performance data; by default at the GPU performance state of capture time, or at an induced state; Concurrent mode (default) lets vertex, fragment and compute overlap like at runtime, Serial mode runs each pass alone for cleaner per-pass numbers that do not represent runtime [P30].
- The Performance timeline has Vertex, Fragment and Compute tracks with each pass's start and duration, aggregated shader tracks, and a Counters timeline (Occupancy, Limiter, Bandwidth); the Counters tab lists counters per pass or command, measured in isolation; the Debug navigator can group commands by pipeline state with each state's share of shader samples [P30]. Xcode 13 introduced this GPU timeline for Apple GPUs [P29].
- Per-line shader profiling: weights next to each source line, a pie chart per line (for example a high "memory sample" share means waiting on texture reads), edits with Reload Shaders that stay inside the debugger [P30]. Apple asks for builds that embed shader source for this view [P30]; whether a Unity player's Metal shaders show readable source in Xcode is UNCONFIRMED FOR 6000.6 (check once).
- On A17 Pro and later, and M3 and later only: the shader cost graph (flame graph of shader function cost) and performance heat maps (section 5) [P30][P35]. Red's machine is an M3 Max [P40], so both are available on the Mac; on an iPhone or iPad they need A17 Pro or newer (inference from [P30]).
- In Metal System Trace the GPU tracks show the shader stages over time; Apple's example finds a 74.64 ms fragment stage behind a skipped frame [P23].

### 3.3 Instruments and the Metal Performance HUD
- Instruments > Game Performance template: Points of Interest, System Load, Thread State Trace, System Call Trace, Virtual Memory Trace, Time Profiler, Thermal State, Metal Resource Events, Metal Application, GPU, Display [P23]. Performance limiter and utilization counters are off by default: Recording Options > Counter Set > Performance Limiters [P23]. A GPU performance state can be induced in Recording Options, and the trace has a GPU performance state track [P29].
- Apple's reading order: Display track for long intervals, then GPU stage durations, then render-thread blocked time, then System Load for preemption (Apple recommends priority 45 for render threads) [P23].
- Metal Performance HUD (quick, no capture): `MTL_HUD_ENABLED=1` (or Xcode scheme > Run > Diagnostics > Show Graphics Overview; on iOS Settings > Developer > Graphics HUD); it shows device, resolution, direct or composited present, app + Metal memory, Game Mode on/off, average fps, GPU time and the frame interval of the last 120 frames [P32]. `MTL_HUD_LOG_ENABLED=1` writes per-frame memory, present interval and GPU time to the console once a second [P32]. `MTL_HUD_ENCODER_TIMING_ENABLED=1` adds GPU time per command encoder, the share per encoder type, a three-frame GPU timeline, and the top three labelled command buffers and encoders, but only if the app does not use Metal counter sample buffers itself [P32]. Apple notes that idle gaps between encoders inflate plain GPU time [P32], which is the same TBDR effect Unity warns about for FrameTimingManager [P2].

### 3.4 Counters and limiters on Apple GPUs
- Limiters to read first: ALU (F16 runs at double the F32 rate), texture read/sample (128-bit formats sample at quarter rate; use mips, ASTC, lossless compression for runtime textures), texture write (pixel size, MSAA sample count), tile memory load/store (threadgroup and imageblock), buffer read/write, GPU last-level cache, fragment input interpolation; memory bandwidth is a separate counter; "a high limiter value does not mean that the workload is efficient" [P17]. On M3/A17 Pro there are also occupancy-manager, shader-launch, L1 and MMU counters [P35].
- Occupancy is the share of the thread pool in use; neither high nor low is a problem by itself [P17].
- HSR is pixel-perfect and order-independent for opaque meshes; its efficiency is read from pixels rasterized, fragment shader invocations, pixels stored and pre-Z test fails; overdraw = fragment shader invocations / pixels stored [P17].
- The Metal debugger's replay is not affected by thermals; Metal System Trace is [P17].

### 3.5 TBDR waste to look for, and where FrontRooms could have it
- Apple's rules: load and store actions use most of an app's system bandwidth and run per render pass, so fewer passes mean less traffic; fold clears into the pass that needs them; store with Don't Care what no later pass reads; make pass-local attachments memoryless; resolve MSAA in the pass that draws it instead of storing samples and reloading them; do not split adjacent passes that write the same attachments, and do not split a pass only because its load/store actions change [P18]. On tile memory the GPU shades only visible primitives and writes each tile once to device memory [P36]. Apple GPUs blend MSAA per sample only at edges [P36].
- Draw order for HSR: opaque first, then alpha-test/discard/depth-writing ("feedback") fragments, then translucent; do not interleave; write all attachments of the pass [P18][P17].
- Unity's views of the same thing: the Frame Debugger shows Color Actions, Depth Actions and Memoryless per render target [P9]; the Render Graph Viewer shows merges, pass-break reasons, load/store per resource and memoryless resources [P13]; iOS has a Memoryless Depth player setting (Unused / Forced / Automatic) [P34], which is `framebufferDepthMemorylessMode: 0` in this project (`ProjectSettings.asset:972`) [P48]; which option 0 maps to is UNCONFIRMED.
- FrontRooms' frame, as structured on 2026-10-02 (WebGL pass list): main-light shadows (2 cascades), additional-light shadow atlas, colour-grading LUT, depth-normals prepass for SSAO, depth copy, SSAO (4 passes), opaque forward at MSAA 4x, MSAA resolve, bloom pyramid (18 full-screen draws), uber post + HUD, final blit [P40]. On 2026-11-04 SSAO off removed only 4 draws, so the prepass no longer doubles draws [P41]. Things to check on the Mac and iPad, in this order (inference from [P18] applied to [P40][P41]):
  1. Is the 4x MSAA colour and depth resolved in the opaque pass and the sample data stored Don't Care, or stored and reloaded for a separate resolve?
  2. After the opaque pass, how many pass breaks reload colour for transparents, glass (Metal Glass RT on Mac), the 60 additive beams of the corridor and the HUD?
  3. Is depth stored because a later pass reads it (SSAO, glass), and is it Don't Care where nothing reads it?
  4. Shadow atlas size: at ULTRA the additional-light atlas is raised to 8192 at runtime [P41]. ESTIMATE: 8192 x 8192 = 67.1 M texels, 128 MiB at 16-bit depth or 256 MiB at 32-bit. The probe read 239.6 MB of render textures in corridor0 at ULTRA and 213.9 MB with SSAO off [P41]; the format of the atlas is what the Frame Debugger "Format" field answers [P9].
- None of these changes the desktop image when done right; the risk is a Don't Care on data that a later pass does read, which shows as garbage, so each change is checked with the image diff (noise floor 0.00-0.07 %) [P41].

## 4. Windows: RenderDoc and PIX on D3D12

### 4.1 RenderDoc (frame debugger, not a profiler; no Metal)
- RenderDoc supports Vulkan 1.4, D3D11 (up to 11.4), D3D12, OpenGL 3.2+ (core) and OpenGL ES 2.0-3.2; Metal is listed only among possible future APIs [P37]. So RenderDoc cannot capture the Mac Editor, a Mac player or an iOS build of FrontRooms, which all run Metal (inference from [P37][P14]).
- RenderDoc's own FAQ: with RenderDoc enabled "timings will change", and it is built for debugging rather than profiling [P37]. Use it for state, targets, meshes and shader inputs, and take timings from PIX or the vendor tools.
- Unity integration (6000.6, Editor only): right-click the Game or Scene view tab > Load RenderDoc (reloads the graphics device), or start the Editor with `-load-renderdoc`; a capture button then appears on the Game and Scene view toolbars; RenderDoc 0.26 or later; the integration is disabled while Unity runs an API RenderDoc does not support; standalone players can be captured with RenderDoc "as normal with no extra setup"; `#pragma enable_debug_symbols` keeps shader names and source but can hurt performance and must not ship [P38].

### 4.2 PIX on Windows (D3D12 timing)
- A GPU capture records every D3D12 call with its data; "Collect Timing Data" replays the capture several times and averages the per-operation GPU time; Execution Duration runs from start-of-pipe to end-of-pipe, EOP Duration from the previous item's end to this one's end; for overlapping async compute take a Timing capture instead; do not use the machine while timing is collected and close other GPU apps; occupancy and hardware counters depend on the GPU vendor and driver; the event list is clearest when the game is instrumented with PIX events [P33].
- Inference: Unity's ProfilingSampler / CommandBuffer sample names reach PIX as event markers; this is UNCONFIRMED FOR 6000.6 and is checked on the first capture.

### 4.3 Unity side on Windows
- Force the API on the player: `-force-d3d12` (or `-force-d3d11` for comparison) [P39]. FrontRooms does not override the Windows graphics API list (no Windows entry under `m_BuildTargetGraphicsAPIs`, `ProjectSettings.asset:547-553`) [P48]; with Auto Graphics API Unity picks the API at runtime [P43], and which one 6000.6 picks on a given PC is UNCONFIRMED, so the capture recipe forces D3D12.
- The Unity Profiler GPU Usage module works on Windows D3D11 and D3D12, in players and in Editor Play mode (with Editor overhead), unless Graphics Jobs is on [P1]. This is the only platform of FrontRooms' where Unity itself can show GPU ms per sampler (inference from [P1]).
- NVIDIA GPUs: Nsight Graphics GPU Trace with the peak-performance-percentage method (throughput-limited above about 80 % of a unit's peak, latency-limited below about 60 %) [P24]. AMD's tools were not researched here.

## 5. Overdraw, quad overdraw and shader cost

### 5.1 Overdraw views
- URP Rendering Debugger > Rendering > Overdraw renders the overdraw debug view, "useful to check where Unity draws pixels over one other" [P11]. The 6000.6 reference lists no separate opaque/transparent modes or a max count [P11], although the clone probe saved both an "overdraw_opaque" and an "overdraw_all" PNG for every view on 2026-11-04 [P41], so the API exposes at least those two (inference; the reference page lags). Needs a Development build in a player, with Strip Debug Variants off for this tab [P12].
- On TBDR the URP view counts what URP submits, while the GPU's HSR removes hidden opaque fragments before shading [P17][P36], so a red opaque area in the URP view may cost little on Apple hardware; transparent and alpha-tested layers cost what they show (inference from [P17][P18]).
- Xcode performance heat maps (A17 Pro+ / M3+): Overdraw mode "visualizes pixels that have been rendered by more than one GPU thread"; also Shader Execution Cost (execution time and latency hiding), Thread Divergence, Instruction Count and Draw ID; clicking a pixel selects its SIMD group and shows its shader execution history [P35][P30]. This is the overdraw that the Apple GPU really executed (inference).
- Counter form of the same: overdraw ratio = fragment shader invocations / pixels stored, read per pass in the Counters tab [P17][P30].

### 5.2 Quad overdraw
- No quad-overdraw view appears in the URP 6000.6 Rendering Debugger reference [P11]. Apple's heat map counts GPU threads per pixel [P35]; whether helper (quad) lanes are included is not stated: UNCONFIRMED. Practical proxy (inference): thin, far geometry (lamp lens rims, baseboards, door edges at 20+ m) shows up as high Instruction Count per covered pixel in the heat map and as low pixels-stored per fragment invocation in the counters.

### 5.3 Shader cost
- Apple: per-line weights and per-line pie charts, call tree, and (A17 Pro+/M3+) the shader cost graph flame graph with jump-to-source [P30][P35]. Sort the Counters table by shader profiler time to find the costliest pass or draw in a shader-bound frame [P30].
- Windows: PIX timing per draw plus RenderDoc shader debugging with `#pragma enable_debug_symbols` in a clone only [P33][P38].
- What to profile first in FrontRooms (inference from [P41]): `FrontRoomsSurface.shader` (83 of 86 surface materials use it), the troffer lens and beam shaders (60 additive beams in the corridor), the glass path (`FrontRoomsMetalGlassRTRendererFeature`, Mac only) and SSAO at full resolution (SSAO is visible: 3.4-9.6 % of pixels change when it is off, so its cost is worth knowing exactly, not cutting) [P41].
