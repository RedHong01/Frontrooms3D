## 1. The change

- **The hold.** `WorldHeld` is true when `FrontRooms3DGame.InspectingNow` is true, or when the last `FrontRooms3DGame.Paused` event said true. The event handler is hooked once per play session at `SubsystemRegistration`, the same way `FrontRoomsInspect` hooks its events. So a screen spawned under the pause card still sees the pause.
- **Screens.**
  - While the world is held, the family's shared focus ray does not run: `focusedScreen` is null and E switches nothing.
  - It also stays off on the frame the world is released (`heldFrame`), so the E that leaves a close-up never switches a CRT too.
  - The ray moved from `Update` to `LateUpdate`. The game and the CRT are both at execution order 0, so in `Update` their order is not fixed. In `LateUpdate`, the E press that opens a close-up is already in `InspectingNow`.
- **Bank.**
  - `Update` pauses the `VideoPlayer` while the world is held.
  - `PrepareIfNeeded` and `OnPrepared` never call `Play` while it is held.
  - On release, `Update` calls `PrepareIfNeeded`, which plays again.
  - Visibility counting goes on as before, so the release needs no bookkeeping.
- **What it does not change.** There are no per-frame allocations: `WorldHeld` reads two statics. There is no platform branch, so desktop, mobile and WebGL behave the same. The codex-audit COV-4 (shared quad), F6 (material) and F7 (LODs) code is untouched.
- **Why it was needed.** The ad bank's `VideoPlayer` runs on `UnscaledGameTime`, so `timeScale 0` does not stop it. In the control run (§3.3), the ad kept running through a close-up, and E switched the CRT under the pause card and while `InspectingNow` was true.

## 6. Notes

- **Landing.** Copy the payload over main's file after checking that main's sha1 is still `ea0c85cf…`. If it is not, merge the diff with `rebase_apply.sh`. The harness stays clone-only and never goes to main.
- **Touch.** The CRT's E reads only the physical keyboard, so on touch a CRT cannot be switched today. That is unchanged here. The hold applies the same way on every platform.
- **Camera.** `ResolveCamera` depends on the first camera it finds, because the game camera has no `MainCamera` tag. In this run that camera was the game camera. A tool or capture camera created before the first CRT spawns would take the focus ray. This is a separate issue and was not changed here.
- **Script order.** The ray now runs in `LateUpdate`. Its pose is the camera's at that point of the frame, which only matters for a 2.4 m focus ray if the rig moves the camera in `LateUpdate` too. The play test showed no difference: focus at 1.2 m in every positive control.
